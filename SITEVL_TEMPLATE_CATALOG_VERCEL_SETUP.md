# Каталог SITEVL: последние настройки Vercel

Ключи не отправляйте в чат. Код подготовлен; production пока не публикуем.

1. Откройте [проект ay-digital-ru](https://vercel.com/vgeniy/ay-digital-ru). Новый проект и новую Redis-базу создавать не нужно.
2. Перейдите в **Storage → Create Database → Blob → Continue**. Выберите **Private**, не Public. Можно подключить уже существующий подходящий приватный store. Проверьте условия тарифа до создания.
3. Подключите store к **ay-digital-ru**, выберите **Production**. В **Settings → Environment Variables** проверьте наличие **BLOB_READ_WRITE_TOKEN** именно для Production. Если подключение добавило только OIDC-настройки, получите read-write token в настройках Blob и добавьте его под этим точным именем. В этой реализации используется явный серверный read-write token.
4. Создайте секрет владельца в своём менеджере паролей: случайный пароль из 64 латинских букв и цифр. Сохраните его как «SITEVL — доступ владельца». Не используйте пароль от другого сервиса.
5. В **Settings → Environment Variables → Add** добавьте **VISITOR_OWNER_API_TOKEN**, значение — только что созданный секрет. Выберите **Production**, включите Sensitive, если доступно, сохраните. Не добавляйте префикс VITE_.
6. Production secrets остаются исключительно в Vercel. **Не копируйте их локально**, не снимайте Sensitive, не используйте env pull/env run для их извлечения. После локальных тестов без secrets создаётся production QA-deployment существующего проекта; там проверяются реальные Blob, Redis, Telegram и owner-доступ. До PASS домен можно оставить на предыдущей READY-сборке через `--skip-domain`. Временный QA flow защищается отдельным случайным ключом, работает только с одной тестовой заявкой, имеет срок действия и удаляется до финальной публикации. Production owner token не возвращается клиенту.
7. **Redeploy потребуется**: после локального PASS выполняется QA-deployment с серверными переменными, реальный E2E и cleanup. Только затем финальный commit/push/deployment без временного QA endpoint. При FAIL основная версия не переключается либо откатывается на предыдущий READY deployment.
8. Напишите: **«Secrets добавлены, продолжай финальный E2E и deploy».**

## Как вы увидите заявку

Telegram-сводка содержит закрытую ссылку `/templates/owner/…`. Откройте её и введите свой ключ владельца. Будут доступны визуальный клиентский сайт, фотографии, контакты, пожелания, бюджет, срок и рекламный источник, а также скачивание полного пакета. Ключ не хранится в адресе или localStorage. «Закрыть доступ» очищает данные вкладки. При смене ключа старый перестанет авторизовать новые запросы после обновления серверного окружения.

## Безопасная проверка готовности

В подготовленном коде **GET `/api/ai-leads` → `templateCatalog`** возвращает только булевы `configured`, `storageConfigured`, `filesConfigured`, `blobConfigured`, `ownerConfigured`. `configured:true` означает наличие настроек, а не доказательство работоспособности credentials. Старый production может ещё не содержать `templateCatalog`.

Без настроек отправка возвращает контролируемый HTTP 503 и `configured:false`, черновик остаётся в браузере. Owner API без owner-ключа возвращает 404, с неверным Bearer — 401. Реальная storage/E2E-проверка до получения credentials остаётся **BLOCKED**.

После финальной QA удаляются только её точно известные временные записи и файлы. Чужие заявки, статистика и Blob-префиксы не затрагиваются. Наличие TTL не заменяет финальную проверку реального удаления.

Справка: [официальная инструкция Vercel Blob](https://vercel.com/docs/vercel-blob/using-blob-sdk). Подготовка не меняет DNS, старые рекламные адреса или production.
